```bash
npx despia-extensions add bluetooth
```

```js
import despia from 'despia-native';

globalThis.onBleDevice = event => {
  event.devices.forEach(device => console.log(device.id, device.name, device.rssi));
};

const radio = (await despia(`extension://ble/state?prompt=${encodeURIComponent(true)}`, ['bleState'])).bleState;
if (!radio?.ok || radio.data.state !== 'on') throw new Error(radio?.code ?? 'no answer');

const scan = (await despia(
  `extension://ble/scan_start?services=${encodeURIComponent('180d')}&seconds=${encodeURIComponent(10)}`,
  ['bleScanStart']
)).bleScanStart;
```

The extension id is `ble`. Every route answers in `ble<Route>` and `onBle<Route>`, for example `bleScanStart`. Set event callbacks before you call a route.

<Warning>
  Needs a physical device for a real radio. The route contract has been run on an iOS simulator and an Android emulator; that proves the routes answer as written, not a radio. The two-phone radio checks are not done yet.
</Warning>

## Install

No values to set. Before you build, give the app its Bluetooth purpose text (`NSBluetoothAlwaysUsageDescription`) in your existing Despia purpose-string settings, and turn on the app's Bluetooth permission (`bluetooth_always`) and, for scanning, its Location permission (`location_when_in_use`). The extension asks Android for the permissions each route needs, one at a time.

| Platform | What the build declares |
| --- | --- |
| iOS | `NSBluetoothAlwaysUsageDescription`; background modes `bluetooth-central` and `bluetooth-peripheral`; state restoration with the central id `main` |
| Android | `bluetooth_always` declares `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE` and `BLUETOOTH_CONNECT`, plus `BLUETOOTH` and `BLUETOOTH_ADMIN` up to API 30, and the `bluetooth` and `bluetooth_le` features as not required. `location_when_in_use` declares `ACCESS_FINE_LOCATION`. `keep_alive` adds a `connectedDevice` foreground service |

A declaration is not consent: the extension requests each runtime permission when a route needs it. On Android 12 and later a scan needs `BLUETOOTH_SCAN` and `ACCESS_FINE_LOCATION`, a link needs `BLUETOOTH_CONNECT`, and advertising needs `BLUETOOTH_ADVERTISE` and `BLUETOOTH_CONNECT`. On Android 7 to 11 a scan needs `ACCESS_FINE_LOCATION`. `state` shows the iOS prompt only with `prompt=true`; call it before the first scan, connect or server route.

## Routes

| Group | Routes |
| --- | --- |
| Radio | `state(prompt)`, `events(after, max, run)`, `keep_alive(enabled)` |
| Central | `scan_start`, `scan_stop`, `devices`, `connect`, `disconnect`, `links`, `discover`, `read`, `write`, `raw`, `subscribe`, `unsubscribe`, `rssi`, `mtu`, `priority`, `phy`, `bond`, `bonds`, `system_devices`, `connection_events` |
| Peripheral | `service_add`, `service_remove`, `services`, `value_set`, `notify`, `advertise_start`, `advertise_stop`, `centrals`, `central_drop`, `respond`, `advertise_set_start`, `advertise_set_stop` |
| L2CAP | `l2cap_publish`, `l2cap_unpublish`, `l2cap_open`, `l2cap_send`, `l2cap_close`, `l2cap_channels` |

Events: `adapter`, `restored`, `device`, `scan_end`, `link`, `value`, `gatt_changed`, `central`, `request`, `advertise_end`, `bond`, `phy`, `connection_event`, `ancs`, `att_request`, `l2cap`, `l2cap_data`, `advertising_set`. Each is also a record in a journal of up to 2000 entries, so a page that was not loaded reads it with `events`, also from the previous launch (`state` answers `run` and `previousRun`).

`scan_start` only starts the scan. Wait for `onBleScanEnd` or poll `state` until `scanning` is false, then read `devices`. `connect` and `subscribe` can post every link change and notified value to your HTTPS server, from a queue that survives a restart.

### Answering reads and writes from the page

Give a characteristic the flag `a` in `service_add` (with `r`, `w` or `c`) and its reads and writes wait for you. The `att_request` event carries `state: "open"`, a `request` number, `kind` (`read` or `write`) and the `central`. Answer it with `respond`: `status` is `ok`, `not_permitted`, `invalid_offset`, `invalid_length`, `insufficient_authentication`, `insufficient_authorization`, `insufficient_encryption`, `not_supported`, `insufficient_resources` or `unlikely`. A request not answered within 25 seconds is answered `unlikely` for you and reported with `state: "expired"`. On iOS every write to such a characteristic waits for `respond`.

### L2CAP channels

An L2CAP channel carries a byte stream without GATT. The peripheral calls `l2cap_publish` and tells the central the `psm` it got, for example in a characteristic. The central calls `l2cap_open` with `id` and `psm` (on iOS, `connect` first). Bytes arrive in `onBleL2CapData`; `l2cap_send` sends up to 2048 bytes; `onBleL2Cap` reports each channel `open` and `closed`.

### Advertising sets (Android)

`advertise_set_start` starts one more advertisement beside `advertise_start`, with Android's advertising set parameters: legacy or extended, connectable, scannable, anonymous, primary and secondary PHY (1M, 2M, Coded), interval, TX power, a scan response and periodic advertising. A set the phone's controller cannot send answers `platform_limit` and names what is missing. On iOS `advertise_set_start` answers `platform_limit`; use `advertise_start`.

## Moving from `bluetooth://`

The built-in `bluetooth://` scheme (iOS only) is removed from the Despia V3 runtime. This extension covers all of it on iOS and Android.

| `bluetooth://` | This extension |
| --- | --- |
| `scan?services&duration` | `scan_start?services&seconds` |
| `stopscan` | `scan_stop` |
| `connect?id&timeout&auto_connect&server` | `connect?id&seconds&auto&server` (`seconds=0`: no time limit, as before) |
| `write` with `text`, `hex` or `value` | `write` with `text`, `hex` or `b64` |
| `window.bluetoothActive` | `state` answers `authorization` |
| Replay queue of 500 events | The journal (2000 records) and `events?run=` for the previous launch |
| Events `device`, `scanEnd`, `connect`, `discovered`, `data`, `writeComplete`, `rssi`, `state`, `raw` | `device`, `scan_end`, `link`, `value`, `adapter`, and each route's answer |

`disconnect`, `discover`, `read`, `raw`, `subscribe`, `unsubscribe` and `rssi` keep their names.

## Platform limits

Each limit is a capability the platform has no public API for. The route answers `platform_limit` and names it, or the answer's `applied` reports the option `false`. Sources read 25 Nov 2026.

- **iOS, connection priority, PHY and bonding.** CoreBluetooth has no API to request a connection interval, read or set the PHY, or start, list or remove a bond. `priority`, `phy`, `bond` and `bonds` answer `platform_limit`. The system pairs when a peripheral requires encryption for an attribute you read or write. Source: [CBPeripheral](https://developer.apple.com/documentation/corebluetooth/cbperipheral).
- **iOS, scanning and advertising.** No scan `mode` and no MTU request (`mtu` answers `requested: false`). No API to drop a central (`central_drop` answers `platform_limit`). An advertisement carries only service UUIDs and a local name, is always connectable, and has no name in the background. In the background, a scan without a service filter stops, and a new one answers `filter_required`. `system_devices` needs `services`. Source: [CBPeripheralManager.startAdvertising](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/startadvertising(_:)).
- **iOS, L2CAP.** A channel opens only to a peripheral the app is connected to, so `l2cap_open` needs `connect` first, and the peripheral's published channel decides encryption. Source: [CBPeripheral.openL2CAPChannel](https://developer.apple.com/documentation/corebluetooth/cbperipheral).
- **iOS reads.** A notification that arrives while a read of the same characteristic is in flight answers that read.
- **Android versions.** `legacy` and `phy` in a scan and the `phy` route need Android 8.0 (API 26), `priority` with `dck` needs Android 14, L2CAP needs Android 10 (API 29) and advertising sets need Android 8.0. Earlier versions answer `platform_limit`. Source: [BluetoothGatt](https://developer.android.com/reference/android/bluetooth/BluetoothGatt).
- **Android bonds and events.** No public API removes a bond; the user removes it in the system Bluetooth settings. `connection_event` comes from the system's connection broadcasts, which carry the device but no service list, so `ids` filter and `services` cannot.
- **Android, other.** No state restoration: links, the server and advertising end with the app's process. Use `keep_alive` to keep links in the background. With `name`, Android advertises the device's own Bluetooth name. A controller without advertising answers `platform_limit`.
- **Both.** One GATT operation runs at a time per link; up to 64 wait. Each has a 10-second timeout that closes the link. Writes are at most 512 bytes. A write without response means the system took the bytes, not that the device got them.
