## When the user taps a push

Put a `path` (and, if you like, `metadata`) in the push's data. When the user taps the notification, Despia V4 does two things, in this order:

1. **It routes the page.** The URL changes to `path` through the History API (`pushState`) and a `popstate` event fires. Most single-page app routers navigate on `popstate` by themselves, so no code is needed. There is no reload.
2. **It calls `window.onNotificationEvent`** once, with `{ type: 'open', path, metadata }`, if your page defines it.

```javascript
// optional: only needed if your router ignores popstate, or you use metadata
window.onNotificationEvent = (event) => {
  // event.type === 'open'
  if (event.path) router.navigate(event.path)
  if (event.metadata) restoreState(event.metadata)
}
```

| App state when the push is tapped | What the page gets |
| :-- | :-- |
| Closed (cold launch) | The tap is held until the page has loaded, then routed and delivered once. |
| In the background | Routed and delivered when the app comes back, with no reload. |
| In the foreground | Nothing when the push arrives (the system shows the banner). Tapping the banner routes and delivers as above. |

This is the same order and payload as on Despia V3, so pages written for Despia V3 keep working unchanged. It is verified on iOS and on Android with OneSignal pushes, in all three app states.

### Send a path from your backend

With OneSignal's REST API, put the path in `data`:

```javascript
body: JSON.stringify({
  app_id: process.env.ONESIGNAL_APP_ID,
  include_external_user_ids: [userId],
  headings: { en: 'Your order shipped' },
  contents: { en: 'Tap to track it' },
  data: { path: '/orders/42', metadata: { orderId: 42 } },
})
```

## OneSignal, or Despia's own notifications

| | OneSignal | Despia notifications |
| :-- | :-- | :-- |
| Package | [OneSignal](/packages/onesignal) (`onesignal`) | [Notify](/packages/notify) (`notify`) |
| Who sends pushes | OneSignal (dashboard or REST API) | Your own server, straight to APNs / FCM |
| Link a push to your user | `dsx.module.onesignal.login({ externalId })` | Save the token from the `notify.token` broadcast on your server |
| Device id | `dsx.module.onesignal.subscription.get()` | `notify.token` broadcast (`{ kind, token }`) |
| Tap routing (`path` → `popstate` → `onNotificationEvent`) | Yes | Listen to `notify.opened` |

Both use the same permission calls on `notify`.

### Listen to the broadcasts

```javascript
if (window.dsx) {
  window.dsx.module.notify.on("opened", (data) => { if (data.path) router.navigate(data.path) })
  window.dsx.module.notify.on("token", ({ kind, token }) => saveTokenOnServer(kind, token))
}
```

`notify.opened` carries `{ id, path, url, data, actionId, userText, coldStart }`.

## Push permission (`nativePushEnabled`)

On Despia V3 you read the `nativePushEnabled` global after `despia('checknativepushpermissions://', ['nativePushEnabled'])`. On Despia V4 that still works (the Legacy polyfill sets it to `true` when the permission is granted or provisional). The modern call gives you the full state:

```javascript
if (window.dsx) {
  const { status, canAsk } = await window.dsx.module.notify.permission.status()
  if (status === "undetermined" && canAsk) await window.dsx.module.notify.permission.request()
} else if (navigator.userAgent.includes("despia")) {
  const { nativePushEnabled } = await despia("checknativepushpermissions://", ["nativePushEnabled"])
}
```

`status` is `undetermined`, `granted`, `limited`, `denied`, `restricted` or `unavailable`.

`notify.permission.status()` never shows a prompt. `notify.permission.request()` asks, and `notify.permission.openSettings()` opens the app's settings when the user said no before. The `notify.permission` broadcast is sent when the answer changes, including when the user comes back from Settings.
